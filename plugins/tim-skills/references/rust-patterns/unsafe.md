# Unsafe contracts and panic safety

**Fit.** Use for raw pointers, manual initialization, custom ownership, or safe wrappers around unsafe operations. First consider a safe operation with the same contract. Ordinary field mutation needs mutable access (such as `&mut self`) unless a valid interior-mutability mechanism applies; marking a function unsafe does not change that. An `unsafe` block transfers proof obligations to the author; it does not relax Rust's validity or aliasing rules.

**Proof boundary.** For every operation identify allocation lifetime, provenance, bounds, alignment, initialization, aliasing, ownership, and thread access. Document the caller's obligations for `unsafe fn` and the local evidence satisfying them at each call. A safe public method must preserve soundness for every safe caller input, including panicking callbacks. Private fields alone do not prove this if safe methods can invalidate them.

**Pointers and references.** A non-null pointer can still dangle or be unaligned. Do not create references to invalid or uninitialized values, even temporarily. `UnsafeCell` permits interior mutation of its contents through shared access but does not permit aliasing mutable references or data races. The immutability of a shared reference to a struct does not itself freeze a separate allocation addressed by a stored raw pointer; separately prove that pointee's access is legal. A pointer derived from an ordinary shared reference does not acquire write permission merely by casting. [UnsafeCell](https://doc.rust-lang.org/std/cell/struct.UnsafeCell.html) · [NonNull](https://doc.rust-lang.org/std/ptr/struct.NonNull.html).

**Partial initialization.** Prefer `Vec::push`, `extend`, or a safe constructor. If raw initialization is justified, distinguish capacity, requested count, and successfully initialized count. `Vec::set_len` requires every newly included element to be initialized and the new length within capacity. Update progress only after a successful write. On unwind, cleanup must cover exactly initialized elements without reading or dropping uninitialized slots; choose an explicit leak or cleanup policy where relevant. `MaybeUninit` does not run the contained destructor automatically. [Vec contract](https://doc.rust-lang.org/std/vec/struct.Vec.html#method.set_len) · [Exception safety](https://doc.rust-lang.org/nomicon/exception-safety.html).

**Drop and pinning.** Restore ownership invariants before a callback can unwind. A destructor may not run on abort or when a value is forgotten, so soundness cannot depend on all callers running cleanup. Model ownership and variance deliberately when using `PhantomData`; copying a historical `#[may_dangle]` example is not a stable-toolchain design. Pin projections and custom `Drop` must respect the pointee's pinning contract; see [async](async-state.md).

**Verification.** Audit the entire safe abstraction, then exercise early return, callback panic, empty and partial progress, and destruction. Miri and sanitizers can expose defects on exercised paths; passing them is not proof that all inputs, targets, or aliasing assumptions are sound. Record unavailable tool/target coverage.
